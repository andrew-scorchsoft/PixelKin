# Copy editing

A house style for editing non-fiction writing so it reads clearly, keeps the
author's voice, and never sounds machine-assembled. Use it for any prose
deliverable: a single paragraph, an email, website or landing copy, a chapter,
an article, a report.

The goal is consistency. Whatever the format, the same standards apply: clear
actors doing clear things, the curse of knowledge broken, the author's spirit
intact, and none of the tells that mark generic AI-flavoured text.

## What good writing optimises for

Every rule below serves one goal: help the reader see something true about the
world as clearly as the author sees it. When two rules conflict, the one that
serves the reader's understanding wins. Writing that serves the writer instead
(impressive, cautious, self-referential) has failed, however polished it reads.

## When to use this skill

Use it for two kinds of task:

- **Editing** — when the user asks to copy edit, polish, tighten, proofread,
  sharpen, de-jargon, "make this read better", or review prose for clarity,
  voice, or flow.
- **Writing from scratch** — when the user asks to draft or write non-fiction
  prose: an email, a blog post, a chapter, a wiki page, marketing copy, a
  report. Write the draft, then edit it against this skill's standards before
  delivering. The standards are identical; for a fresh draft you are simply
  your own first editor.

It does **not** apply to code comments, commit messages, reference API
documentation, or fiction.

## What this skill governs — and what it leaves to you

This skill governs writing **craft**: clarity, voice, sentence vigour, flow,
coherence, credibility, and the absence of AI tells. These hold for every form
of writing — a blog post, a book chapter, an email, a wiki page, a report, a
landing page.

It does **not** prescribe the overall shape of a document. A blog post, a
chapter, an email, and a wiki page each have their own valid structures, and
the same writing can often work in more than one shape. Decisions about overall
structure — what order the sections go in, whether there is an opening hook,
whether the piece closes with takeaways — belong to the writer and the format's
own conventions, not to this skill. Where the guidance below touches structure,
treat it as an optional consideration, not a required template. Improve the
writing within whatever structure the piece uses; do not impose a new one
unless the user asks for it.

## First: orient yourself

Before writing or editing, settle four things. Ask the user only if you
genuinely cannot infer them.

1. **Format.** Standalone paragraph/passage, email, website/marketing copy,
   wiki or knowledge-base page, blog post, long-form (chapter/article/report),
   or anything else. The format shifts which considerations matter — see
   `references/format-playbooks.md`. It does not lock the piece into a fixed
   structure; the list of formats there is illustrative, not exhaustive.
2. **Audience and register.** Who reads this, and how formal is the
   relationship? A cold sales email and an internal note edit differently.
3. **English variant.** Default to **UK English** (spelling, grammar,
   punctuation). If the surrounding project clearly uses US English, or the
   user says otherwise, match that and stay consistent throughout.
4. **Voice constraints.** If a project defines house style, a phrase bank, an
   anti-language list, or load-bearing defined terms, honour them. Read any
   project style file before editing.

## Editorial priority order

Edit in this order. Earlier items outrank later ones — never sacrifice meaning
for rhythm.

1. **Meaning and accuracy** — the text says what it intends, and it is true.
2. **Reader comprehension** — a smart reader outside the field can follow it.
3. **Flow and coherence** — ideas follow in a sound order and the piece holds
   together within whatever structure it uses (this is internal coherence, not
   a prescribed shape).
4. **Voice preservation** — the author still sounds like themselves.
5. **Style consistency** — terminology, formatting, conventions hold throughout.
6. **Grammar, punctuation, spelling** — correct, and in the right English variant.

Do not rewrite for the sake of rewriting. If a sentence already works, leave it
alone. Over-editing into bland correctness is a failure, not a success.

## Core copy-editing rules

These apply to every format.

1. **Preserve meaning and voice.** Keep the original nuance, emphasis, and the
   author's natural strengths — direct address, practical explanation,
   concrete examples, occasional wit. Do not make prose sound corporate,
   robotic, pompous, or over-polished.

2. **Clarity and readability.** Remove ambiguity, tighten vague wording,
   simplify inflated phrasing. Prefer plain, precise words over elaborate
   ones — but do not oversimplify useful language or flatten nuance. Break
   tangled sentences. Make relationships between ideas explicit. Prefer
   affirmative phrasing over negatives; stacked negatives ("not uncommon",
   "cannot … unless") slow the reader down (see Pinker rule 14).

3. **Sentence style.** Active voice by default. Keep the passive only in the
   three cases where it genuinely serves the reader (see Pinker on the passive
   voice): topic continuity ("The first proposal *was rejected* within
   minutes"), an unknown or irrelevant agent ("The file *was deleted*
   overnight"), or end-weight (moving a long agent phrase to the emphatic
   end). Kill it when it hides responsibility ("mistakes were made"). Prefer
   direct subject-verb-object. State the main action early; do not bury the
   verb under setup. Keep grammatically linked words close (subject near verb)
   and put heavy phrases last, so the reader is not holding structure open in
   mind. Use parallel structure in lists. Vary sentence length and shape so
   the prose has rhythm.

4. **Flow and coherence.** Improve transitions between sentences and
   paragraphs. Make logical relations explicit with connectives (*because,
   but, so, nevertheless*) rather than leaving the reader to guess the link.
   Introduce an entity before referring back to it as "the X". Reduce
   repetition across nearby sentences. Move material only when it genuinely
   improves order. Do not invent transitions to material that is not present.

5. **Concision.** Cut redundancy, filler, empty intensifiers, throat-clearing,
   and repetitive restatement. But keep warmth, setup, and voice that genuinely
   helps the reader — concision is not amputation.

6. **Punctuation as judgement, not superstition.** Use em dashes, en dashes,
   colons, semicolons, commas, and parentheses where they improve clarity or
   rhythm. Ban no mark outright. But do not overuse em dashes — if the prose
   turns jumpy or overdramatic, swap some for commas, parentheses, or full
   stops. Use hyphens in compound modifiers for clarity.

7. **Cut metadiscourse, keep signposting.** Cut sentences where the writing
   talks about itself rather than its topic — "in this section I will
   argue…", "as previously mentioned…", "this is what this chapter is about".
   Replace them with a substantive claim, or delete them. **Keep** functional
   navigation: headings, forward references, explicit promises, bridges. The
   rule targets prose that performs its own structure, not aids that help the
   reader move.

8. **Kill zombie nouns.** Nouns ending in *-ion*, *-ment*, *-ance*, *-ity*
   paired with weak verbs (*occurred*, *took place*, *was carried out*, *is the
   mechanism by which*) hide the real action. Turn the noun back into its
   verb. *"The anticipation of a cancellation occurred"* → *"We anticipated
   they would cancel."* Exception: do not flatten load-bearing terms-of-art the
   project has defined and uses consistently.

9. **Examples must do work.** Keep examples, analogies, and stories that aid
   understanding, memorability, or persuasion. Tighten or cut ones that repeat
   a point, take too long to land, feel indulgent, or merely decorate.

10. **Credibility.** Flag overstatement that weakens trust. Specific, defensible
    claims beat sweeping ones. Do not invent facts, examples, statistics, or
    quotations. Where a claim needs support and a source is missing, flag it
    rather than inventing one.

## The Pinker pass

After the core rules, review against the classic-style principles in
`references/pinker-principles.md`. The essentials:

- **Window, not diary.** Write as if pointing at the world, not narrating your
  own thought process. Cut professional narcissism.
- **Break the curse of knowledge.** Define jargon and acronyms on first use.
  Never assume the reader knows what you know.
- **Topic first, emphatic end.** Start a sentence with what the reader already
  knows; end with the new, important word so it lands.
- **Replace zombie meta-concepts** (*paradigm, framework, perspective,
  strategy* used vaguely) with concrete nouns and verbs.
- **Respect working memory.** Keep linked words close, resolve pronouns
  quickly, avoid garden-path sentences, and prefer affirmatives to negatives.
- **Keep the model coherent.** Make logical links explicit with connectives,
  introduce an entity before referring back to it, and hold one thread.
- **Ignore bogus grammar rules** (split infinitives, sentence-final
  prepositions, singular *they* are all fine); enforce real semantic
  distinctions.

## The AI-tells pass

Before delivering, scan for the patterns that mark generic machine-written
prose, using `references/ai-tells.md`. The high-frequency offenders:

- Formulaic structure: every section as intro → explanation → example →
  takeaway; heavy "firstly/secondly/finally" signposting; conclusions that
  merely restate the intro.
- "Not X, but Y" constructions stacked up; relentless three-part lists.
- Hype verbs (*unlock, empower, elevate, transform, leverage*) and AI-cluster
  words (*delve, landscape, realm, tapestry, robust, seamless, nuanced*).
- Filler phrases ("it's important to note", "in today's fast-paced world",
  "let's dive in", "ultimately").
- Symmetrical paragraph lengths and similarly shaped sentences; perfect grammar
  but sterile rhythm; em dashes overused beyond the author's normal style.
- Broad claims with no concrete example, name, date, number, or real incident.

The human check: *Could anyone have written this paragraph? Does it sound like
something this author would actually say? Is there a specific, defensible,
memorable point?* If not, fix it.

## Format-specific considerations

Different formats raise different things worth checking. These are
*considerations*, not templates — they never override the structure the piece
or its format already calls for. Read `references/format-playbooks.md` for the
format in front of you. In brief:

- **Paragraph / passage** — sentence- and paragraph-level only. Do not force
  restructuring or invent transitions to absent context.
- **Email** — usually clearer to lead with the point or the ask; keep one
  email to one purpose where you can; make any action (who, what, by when)
  explicit; cut "I hope this finds you well" openers; match register to the
  relationship.
- **Website / marketing copy** — lead with reader benefit; keep it scannable;
  prefer concrete over adjectival; make any call to action clear; kill
  unearned hype.
- **Wiki / knowledge-base page** — make it findable and skimmable; state the
  answer before the background; keep it accurate and easy to maintain.
- **Long-form (chapter, article, report)** — coherence questions worth
  considering: is there a clear through-line, do sections follow in a sound
  order, do examples land where the reader needs them, is there drift or
  self-repetition. Apply the ones that serve the piece; do not impose a
  standard opening, heading scheme, or ending it was not written to have.

## Output

By default, **return only the finished text** — the edited copy, or the draft
you were asked to write — with no commentary, no explanation of changes, and no
repeating these instructions.

If the user asks for a rationale, a change summary, or tracked changes, provide
the clean text first, then the explanation separately below it.

If editing reveals a factual problem, an unsupported claim, or an ambiguity you
cannot resolve, do not silently paper over it — deliver the best edit you can
and flag the issue to the user.

## Guiding principle

Edit like a skilled non-fiction editor, not a rule-enforcer. Protect the
reader's experience. Preserve the author's voice. Improve the writing where it
matters. Leave alone what already works.
